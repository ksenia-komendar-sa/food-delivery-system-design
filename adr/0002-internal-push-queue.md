# ADR-0002. Отдельная внутренняя очередь push-сообщений после сервиса уведомлений

## Контекст

Сервис уведомлений читает бизнес-события из Kafka и в итоге должен вызвать API внешних провайдеров — FCM и APNs. Между этими двумя точками нужно определить, как построен путь сообщения: воркеры читают Kafka напрямую или готовые сообщения сначала попадают в отдельную очередь, откуда их читают воркеры.

## Варианты

**Вариант 1. Воркеры читают напрямую из Kafka и сами работают с шаблонами и настройками пользователя.**

- Бизнес-логику — opt-in, шаблоны, работу с токенами — придётся дублировать в каждом воркере.
- Воркер должен сам разворачивать событие в несколько сообщений. У пользователя может быть несколько устройств: телефон, планшет, второй телефон. Одно событие «заказ отменён» — это три сообщения.
- Retry получается на уровне события. При повторной обработке событие снова развернётся в три сообщения, и уже доставленные уйдут повторно.

**Вариант 2. Сервис уведомлений валидирует событие, применяет настройки пользователя и шаблон, обрабатывает токены и передаёт готовое сообщение в очередь, откуда его читают воркеры.**

- Вся бизнес-логика сосредоточена в сервисе уведомлений. Воркер отвечает только за техническое взаимодействие с API своего провайдера: формирует запрос, отправляет уведомление, обрабатывает ответ или ошибку.
- Retry работает на уровне сообщения: если APNs вернул ошибку, повторяется одно конкретное сообщение.

## Решение

Выбран второй вариант, потому что в Kafka и во внутренней очереди лежат разные сущности. В Kafka — бизнес-событие «заказ № 42 отменён». В очереди — готовое сообщение с текстом по шаблону, конкретным токеном и конкретным провайдером. Разделение даёт корректный retry без дублирования сообщений и не требует дублировать бизнес-логику в воркерах.

## Последствия

- Появляется ещё один компонент — сама очередь. Её нужно разворачивать, мониторить накопление сообщений, обрабатывать переполнение.
- Сообщение проходит два звена вместо одного, задержка доставки увеличивается.
- Реализация очереди не зафиксирована. Вариант с отдельным топиком в Kafka не требует нового инструмента; альтернатива — RabbitMQ.
