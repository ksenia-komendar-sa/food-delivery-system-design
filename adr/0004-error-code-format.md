# ADR-0004. Формат кодов ошибок в теле ответа

## Контекст

В API три ответа с ошибками: `400`, `429`, `500`. Тело ошибки одинаковое и состоит из `code` и `message`. Нужно определить, что содержится в `code`.

## Варианты

**Вариант 1. Только HTTP-статус, без поля `code`.**

Клиент смотрит на `response.status`, в теле остаётся один `message`. Под `400` в дальнейшем может быть скрыто несколько разных ситуаций, и различить их можно будет только по `message` — а этот текст меняется, локализуется и правится, полагаться на него ненадёжно.

**Вариант 2. Числовой `code`, повторяющий HTTP-статус.**

Не несёт новой информации: статус уже передан в статус-строке ответа.

**Вариант 3. Числовой внутренний реестр** — например, `1020`, `2015`, часто с группировкой диапазонами: `10xx` — авторизация, `20xx` — валидация.

Компактно, удобно хранить и группировать. Но требует внешнего справочника: без него код неинформативен ни для разработчика клиента, ни для тестировщика.

**Вариант 4. Строковый машиночитаемый код.**

Понятен сразу, без обращения к справочнику. `enum` в спецификации делает перечень закрытым: клиент может обработать все случаи, генератор создаёт типизированный набор значений.

При добавлении методов с бизнес-логикой под одним статусом `400` окажется несколько ситуаций с разной реакцией клиента: недоступный товар, просроченный промокод, адрес вне зоны доставки. Различить их по статусу станет невозможно, а разбирать `message` ненадёжно.

## Решение

Строковый `code` с закрытым перечнем: `INVALID_QUERY_PARAM`, `RATE_LIMIT_EXCEEDED`, `INTERNAL_ERROR`.

Один код может покрывать несколько причин, если клиент реагирует на них одинаково. У ответа `400` три причины — неверный `limit`, `offset` или `sort`. Во всех трёх случаях приложению нужно сделать одно и то же: понять, что ошибка в его собственном запросе, и записать её в лог для разработчика. Поэтому код один — `INVALID_QUERY_PARAM`, а какой именно параметр не прошёл, написано в `message`. Отдельные коды нужны там, где отличается поведение клиента: при `429` приложение ждёт и повторяет запрос, при `500` показывает пользователю сообщение о сбое.

## Последствия

- В текущем виде поле `code` избыточно: каждому из трёх кодов соответствует ровно один HTTP-статус, и клиент мог бы различать ситуации по статус-строке. Польза появится при расширении API.
- Добавление нового кода требует изменения спецификации. Это обратно совместимое изменение — существующие клиенты продолжают работать, попадая в ветку «неизвестная ошибка», поэтому новая мажорная версия API не нужна.
- Клиент обязан предусмотреть обработку неизвестного кода, иначе при расширении перечня он сломается.
