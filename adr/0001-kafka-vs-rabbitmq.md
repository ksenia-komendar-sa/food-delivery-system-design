# ADR-0001. Kafka как шина событий для доставки уведомлений

## Контекст

Для мобильного приложения по доставке продуктов нужно спроектировать архитектуру отправки push-уведомлений для оповещения пользователей о заказах и о рекламных акциях.

## Варианты

Для отправки событий в сервис уведомлений можно выбрать три варианта: Kafka, RabbitMQ, синхронные HTTP-вызовы из сервисов напрямую в сервис уведомлений.

Асинхронное взаимодействие представлено брокерами Kafka и RabbitMQ. Kafka имеет преимущество, потому что позволяет обрабатывать события повторно. Например, если была ошибка в шаблоне и какой-то период времени пользователи получали push с битым текстом, то в Kafka можно подвинуть offset и обработать события заново. В RabbitMQ такой возможности нет: сообщение исчезает сразу после подтверждения.

Kafka больше подходит для сервиса доставки, потому что одно событие в дальнейшем будут читать несколько сервисов — например, к сервису уведомлений добавятся аналитика, бонусная система, история заказов. Если бы приложение не планировалось дорабатывать и расширять, подошёл бы RabbitMQ.

Синхронные HTTP-вызовы потребуют при появлении нового консьюмера правок во всех шести существующих сервисах. Также минусом будет сильная связанность сервисов: при недоступности сервиса уведомлений упадёт создание заказа — сбой в некритичной подсистеме станет сбоем в критичной. В Kafka и RabbitMQ консьюмеры добавляются независимо, их просто подключают к брокеру.

## Решение

Для отправки событий в сервис уведомлений выбрана Kafka. Она позволяет обрабатывать события повторно, и одно событие могут читать несколько сервисов.

## Последствия

- Kafka сложнее в эксплуатации, чем RabbitMQ: нужен кластер, продуманное партиционирование, мониторинг лага консьюмеров. Для небольшой команды это заметная нагрузка.
- Возможны дубли событий, так как доставка работает по принципу at-least-once. Дедупликация в текущей версии не реализована. Вариант решения — проверка по идентификатору события перед отправкой; идентификаторы обработанных событий хранятся в таблице с уникальным индексом или в Redis с TTL.
- При асинхронной доставке возможна задержка: push приходит не сразу после события. Задержка в пределах секунд, для push-уведомлений это приемлемо.
- Порядок в Kafka гарантируется только в рамках партиции: два события по одному заказу могут попасть в разные партиции и обработаться не по порядку. Решается ключом партиционирования — например, по `order_id`.
